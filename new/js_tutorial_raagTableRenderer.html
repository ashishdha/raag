Reading raagTableRenderer.js

This page walks through every construct used in raagTableRenderer.js, one concept at a time. You already know ChucK, so wherever JavaScript does something with a genuinely different mindset — dynamic typing, closures, the DOM, events — this page calls it out explicitly and compares it to the ChucK way of doing the same job. Where JS is basically "the same idea, different keyword," it says so quickly and moves on.

Use the contents on the left as a map — each entry jumps straight to that concept, and each section ends with a link back up. There's no need to read top to bottom in one sitting; treat it like a reference you dip into while rereading the actual code.

# The big picture

renderRaagTable() does one job: given a currentRaag object, draw a table with one row per property. Column 1 is the property's name, column 2 is a human-readable, sometimes-editable box, column 3 is the raw stored value.

Structurally, the file is one outer function containing four small helper functions and a loop. Nothing in it runs on its own — like a ChucK fun, it only does anything when something else calls it. The first call happens whenever your own code decides the table needs to exist or refresh (e.g. right after currentRaag.set(...) finishes). After that, the function calls itself again each time the person edits a field — that's covered in full in The render cycle once all the pieces are on the table.

🎼 ChucK bridge

There's no shred here, no now => now, no audio-rate loop. A JS function that touches the page runs synchronously from top to bottom exactly once per call, then hands control back to the browser — much like calling one of your ChucK class's fun methods once, rather than spawning a shred that keeps running.

# Doc comments — /** ... */

The block at the top of the file is a JSDoc comment. It's still just a comment — the engine ignores it completely — but its specific shape (/** to open, @param tags for each parameter) is a convention that editors like VS Code understand. Hover over a call to renderRaagTable(...) anywhere else in your project and the editor will pop up this exact description, including which parameters are optional.

The square brackets around [onEdit] in @param {function} [onEdit] is JSDoc's way of marking a parameter optional — that's a documentation convention, not JS syntax; the real optionality is handled by the language itself, covered next.

🎼 ChucK bridge

This plays a similar role to the comment banners you already write above your ChucK functions (like the // ============ header blocks in Raag_class), just in a format tools can parse. ChucK has no built-in equivalent that editors read automatically.

# The function & its parameters

function renderRaagTable(currentRaag, containerEl, onEdit) {

Three parameters, no types written anywhere. currentRaag will be your Raag instance, containerEl an existing, empty DOM element to build the table inside, and onEdit is optional — if the caller doesn't pass a third argument, JavaScript doesn't error out; onEdit is simply undefined inside the function body. That's what the guard in The optional onEdit hook checks for.

🎼 ChucK bridge

In ChucK every parameter is typed and every call must supply all of them — which is exactly why your own Raag_class defines pairs like fun int generic_svar_info(int id1, int id2) and a zero-argument fun int generic_svar_info() that just calls the first with defaults. That's ChucK's way of faking an optional parameter: write two overloads. JS doesn't need the second overload — one function, with an argument you're free to omit, does the same job. The trade-off is that JS won't stop you from forgetting an argument by accident; there's no compiler catching it, only whatever check you write yourself (like the typeof guard here).

# The Set

const EDITABLE_PROPERTIES = new Set([
  'name', 'aaroh', 'avaroh'
]);
...
const editable = EDITABLE_PROPERTIES.has(key);

A Set is a built-in collection that stores unique values and answers one question fast: "do you contain this?" — .has(value) returns true or false. It's the right tool here because that's the only question ever asked of EDITABLE_PROPERTIES and SVAR_ARRAY_PROPERTIES: is this particular key in the list.

A plain array could hold the same strings, but checking membership would mean writing your own loop (or calling .includes(), which loops internally) every single time. Set exists specifically so "is X in this collection" reads as one clear method call instead of a loop you have to re-justify every time you see it.

🎼 ChucK bridge

This is the same category of problem your Array class's find(lookupValue, lookupArray) solves — loop through, compare each element, return whether/where it matched. Set.has() is JS's built-in version of exactly that idea, minus writing the loop yourself.

# Scope & closures

Notice where EDITABLE_PROPERTIES, SVAR_ARRAY_PROPERTIES, and all four helper functions (isChainArray, toHumanReadable, fromHumanReadable, toRawString) are declared: inside renderRaagTable, not above it at the top of the file. That placement is deliberate — it means nothing outside this function can see or touch them, and they don't pollute whatever else lives in your project's global scope.

The helper functions can still reference EDITABLE_PROPERTIES and SVAR_ARRAY_PROPERTIES even though those aren't passed in as parameters — that's a closure. Any function remembers the variables that were in scope where it was defined, not just the ones handed to it explicitly. Because toHumanReadable is defined inside renderRaagTable, it closes over (keeps access to) everything declared above it in that same function body.

worth knowing

Because they're declared inside the function, both Sets and all four helpers get rebuilt from scratch on every single call to renderRaagTable — including the recursive redraw after an edit. At ~80 rows that's irrelevant, but it's a real trade-off: simplicity (everything the function needs lives right there, easy to read top to bottom) versus a small, repeated cost. If this were rendering thousands of rows on every keystroke, you'd move the two Sets above/outside the function so they're built once, ever. Try it yourself — see Exercises.

const just means the variable name itself can't be reassigned to point at something else — it does not mean the value is frozen. table, row, and the two Sets are all declared const, yet the code still calls methods on them (row.appendChild(...)) that change their contents. What const forbids is table = somethingElse later on — reassigning the variable, not mutating what it points to.

🎼 ChucK bridge

ChucK's class-scope variables (declared once at the top of Raag_class, like int aaroh[0];) are visible to every fun in that class without being passed as parameters — same underlying idea as a closure: code declared "inside" a surrounding scope can see that scope's variables. The difference is that ChucK's version is tied to the whole class instance and lasts as long as the instance does; a JS closure is tied to one specific call of the outer function, and a fresh one is created every time you call it again.

# Arrow functions

value.every(v => Array.isArray(v))
value.map(chain => intArray2string(chain))
displayInput.addEventListener('change', () => { ... });

v => Array.isArray(v) is a small, unnamed function — take one input (v), return the result of one expression, no function keyword, no { } or explicit return needed for a single expression. It's used here purely as a value to hand to another function: .every(), .map(), and addEventListener() all expect "a function to call later" as one of their arguments, so these are written right where they're needed instead of being declared, named, and referenced separately.

The () with nothing inside, in () => { ... }, means the function takes no arguments — that's the change event handler, which doesn't need any input to do its job; everything it needs (key, displayInput) is already available via closure.

🎼 ChucK bridge

ChucK doesn't have an equivalent — functions there are always declared with fun and a name. The nearest JS relative of a named fun is a regular function toHumanReadable(...) { ... } declaration (used for the four helpers here). Arrow functions are specifically for the "quick, throwaway, defined right where it's used" case, which ChucK doesn't really have a shorthand for.

# every, map, join

Three array methods do most of the data-shaping work in this file:

  • .every(fn) — checks fn against every element and returns one true/false. isChainArray uses it to ask "is every item in this array itself an array?"
  • .map(fn) — runs fn on each element and returns a new array of the results, same length, original untouched. Used twice: turning each chain into a display string, and (recursively) turning each raw value into its string form.
  • .join(separator) — glues an array of strings into one string, with separator between each pair. ['S','R','G'].join(', ') becomes "S, R, G".

These are typically chained: value.map(chain => intArray2string(chain)).join(' | ') first turns an array of chains into an array of strings, then glues those strings together with a visible separator.

worth knowing

.every() on an empty array always returns true, for any condition — there's nothing to fail the check on, so it's vacuously true. That means isChainArray([]) is true: an empty array can't be told apart from an empty 2D array just by looking at its shape. Harmless here (both cases end up displaying nothing), but it's a classic edge case worth having a reflex for — "empty passes .every(), always."

🎼 ChucK bridge

Every one of these replaces a for (int i; i < arr.cap(); i++) loop you'd write by hand in ChucK. .map() is the closest thing to what your own Array class's reset()/rotate() functions do manually: build a brand-new array by transforming each element of an old one.

# typeof & dynamic typing

if (typeof value === 'boolean') { ... }
if (typeof value === 'number' && !Number.isInteger(value)) { ... }
if (typeof onEdit === 'function') { ... }

typeof returns a string naming the runtime type of whatever follows it: 'number', 'string', 'boolean', 'function', 'undefined', or 'object'. This code checks type at runtime because it has to — a single property on currentRaag could hold a number, a string, a boolean, or an array depending on which one it is, and nothing in the language forces it to declare that ahead of time.

worth knowing

typeof is a genuinely quirky tool. typeof [] is 'object' (arrays are objects under the hood) and, even stranger, typeof null is also 'object' — a decades-old bug in the language that's now permanent for backwards compatibility. That's exactly why this file never writes typeof value === 'object' to detect arrays — it uses the dedicated Array.isArray() instead, and checks value === null with a plain equality comparison rather than typeof.

🎼 ChucK bridge

This is the biggest mental shift coming from ChucK. In Raag_class, every single variable declares its type up front — int aaroh_jaati;, float shuddhataa_rank; — and the compiler enforces it before your code ever runs; putting a string into an int variable simply won't compile. In JS, a variable is just a label that can point at any kind of value, and it can point at a different kind of value tomorrow. Nothing stops you from writing let x = 5; x = "hello"; — both lines are completely legal. That flexibility is exactly why typeof exists: since the "shape" of a value isn't nailed down by the language, code that needs to behave differently for different types has to ask, in real time, "what actually is this thing right now?"

# Recursion — twice, in two different flavors

A function calling itself shows up twice in this file, doing two genuinely different jobs.

1. Computing a value — toRawString:

function toRawString(value) {
  if (value === null || value === undefined) return '—';
  if (Array.isArray(value)) {
    return '[' + value.map(toRawString).join(', ') + ']';
  }
  return String(value);
}

For a nested array like saa_pa_chains (an array of arrays), each inner array also needs the [a, b, c] treatment. Rather than writing separate logic for "one level deep" and "two levels deep," toRawString calls itself on each element via value.map(toRawString). Every recursive function needs a base case — a condition where it stops calling itself and just returns a plain answer. Here that's return String(value): the moment value isn't an array anymore, the recursion bottoms out.

2. Restarting a process — renderRaagTable:

renderRaagTable(currentRaag, containerEl, onEdit); // redraw with fresh calculated values

This is a different shape of recursion — not "compute a smaller version of the same question," but "when something changes, throw the whole table away and build it again from scratch." It's safe specifically because every call starts with containerEl.innerHTML = '', so there's never leftover state from the previous call to worry about. This call only ever happens from inside a change event handler — triggered by an actual person editing an actual field — so it can never spin in an uncontrolled loop the way a recursive function with no base case (or a ChucK while(1) with nothing pausing it) would.

# null vs undefined

if (value === null || value === undefined) return '';

JS has two different "nothing" values. undefined is what you get automatically — a variable that was declared but never assigned, an object property that was never set, a function parameter nobody passed in (like onEdit when it's omitted). null is a "nothing" someone had to write on purpose, usually meaning "this exists as a concept but deliberately has no value" — exactly how your Supabase columns use it, per your own project convention: NULL means "not yet entered," not zero, not empty string.

This check catches both, because a freshly-constructed currentRaag could have properties that are still JS's default undefined, or properties explicitly set to null to mirror an un-classified database column. Either way, the table should show a blank box rather than the literal text "null" or "undefined."

worth knowing

This is exactly why the check happens before String(value) is ever reached. String(null) genuinely returns the three-character string "null", and String(undefined) returns "undefined" — without the guard at the top, every unset field would visibly display that word instead of being blank.

# Building strings

return '[' + value.map(toRawString).join(', ') + ']';

+ between strings concatenates them, same as most C-family languages. This isn't the only way to build a string in modern JS — template literals, written with backticks, let you embed values directly: `[${value.join(', ')}]` instead of '[' + value.join(', ') + ']'. This file sticks to plain + concatenation throughout, which is perfectly normal and arguably clearer for something this short — but template literals are worth knowing, since you'll see them constantly in other JS code (including elsewhere in this project, e.g. raags_search.js).

# createElement & friends

const row = document.createElement('tr');
row.className = editable ? 'row-editable' : 'row-calculated';
nameCell.textContent = key;
row.appendChild(nameCell);

This is JS building HTML by hand instead of you writing it as static markup. document.createElement('tr') makes a brand-new, empty <tr> element that doesn't exist on the page yet — it's just sitting in memory. Setting .className is the same as writing class="..." in HTML directly. .appendChild(child) is what actually places one element inside another, building up the tree; nothing appears on the actual page until the finished tree gets attached to something already on it (the last line of the function, containerEl.appendChild(table), is what finally makes all of this visible).

Two different ways of putting text into an element show up here, deliberately: .textContent and .innerHTML. nameCell.textContent = key inserts key as plain text, exactly as-is, no matter what characters it contains. thead.innerHTML = '<tr><th>...' instead parses the string as actual HTML markup and builds real <tr>/<th> elements from it.

worth knowing

innerHTML is only used twice in this file, and both times on a fixed string you wrote yourself — the header row, and containerEl.innerHTML = '' to clear it out. It is never used for anything that came from currentRaag. That's not an accident: if a property value ever contained characters that look like HTML (say, a name with a stray < in it), running it through innerHTML would let it get parsed as markup instead of shown as text — everywhere actual data gets displayed (nameCell.textContent, rawOutput.textContent, displayInput.value), this file uses .textContent or .value instead, which never parses anything, ever. Good general rule: innerHTML only for markup you wrote; textContent/ .value for anything that came from data.

# Object.keys() & iteration order

for (const key of Object.keys(currentRaag)) {
  ...
}

Object.keys(obj) returns a plain array containing the name of every property obj owns, as strings — ['name', 'aaroh', 'avaroh', 'thaat_id', ...]. for (const key of someArray) then visits each one in turn, handing you the value (here, each key string) directly — no index variable needed unless you ask for one. This is different from the C-style loop you'd write in ChucK (for (int i; i < arr.cap(); i++)), where you get an index and have to look up arr[i] yourself; for...of skips straight to the element.

Crucially, this relies on a real guarantee, not luck: for plain string property names (which is all of these — none of your column names are pure numbers), JS iterates them in the exact order they were first assigned. Since your class constructor assigns properties in the same order as the ChucK class declaration (per your project's convention), this loop naturally produces table rows in that same Minimal → Maximum tier order, with zero sorting logic needed.

# input, output, and readonly

displayInput.readOnly = true;
...
const rawOutput = document.createElement('output');

Column 3 deliberately uses <output> rather than another <input> — it's the semantically correct element for "the result of a calculation," and browsers/screen readers treat it accordingly. It's never interactive at all, so there's no editable-vs-not distinction to manage for it.

Column 2 always uses an <input>, editable or not, so both states look and behave consistently (selectable, copyable text in a box) — the only difference is the readOnly property. One naming gotcha worth flagging: in JS, DOM properties are always camelCase — input.readOnly — even though the matching HTML attribute is written lowercase, <input readonly>. Setting displayInput.readOnly = true from JS is exactly equivalent to typing readonly in the HTML by hand.

worth knowing

readonly and disabled are not the same thing, even though they look similar. A readonly input can still be focused, selected, and copied from — just not typed into. A disabled input is entirely inert: it can't be focused, its text is harder to select, and — important if this ever lives inside a real <form> — disabled fields don't get submitted at all. This file uses readOnly specifically so you can still click into a calculated cell and copy its value out.

# Events — addEventListener

displayInput.addEventListener('change', () => {
  currentRaag[key] = fromHumanReadable(key, displayInput.value);
  if (typeof onEdit === 'function') onEdit(key, currentRaag[key]);
  renderRaagTable(currentRaag, containerEl, onEdit);
});

addEventListener(eventName, callback) registers a function to be called later, whenever that named event happens on that element. It does not run callback immediately — it hands the browser a function and says "hold onto this, and call it for me when the moment comes." 'change' specifically fires once a text input's value has been committed — on blur (clicking/tabbing away) or pressing Enter — not on every individual keystroke. That's a deliberate choice here: it means the table only redraws once you're actually done typing, rather than on every letter (the event 'input' would fire on every keystroke instead, if you ever wanted that behavior).

🎼 ChucK bridge

The closest thing you already know is a ChucK Event: a shred calls .wait() on it and the VM suspends that shred until something else .broadcast()s it, then resumes exactly where it left off. Browser events work toward the same goal — react to something happening later, without polling for it in a loop — but the mechanics differ. Nothing here pauses. By the time the person actually edits a box, renderRaagTable finished running and returned a long time ago; the browser kept the little arrow function you handed it in memory, and calls it fresh, independent of anything else your code is doing at that moment.

# Your class, revisited

currentRaag is an instance of the Raag class you wrote — presumably built with something like this.aaroh = [...] for each property inside its constructor. Object.keys(currentRaag) only returns properties that instance actually owns — the ones assigned directly onto it, typically in the constructor. Methods you define in the class body (things like a hypothetical currentRaag.set(...)) live on the class's prototype, shared by every instance, not copied onto each individual object — so they're automatically excluded from this loop with zero filtering code needed. That's what lets the table only ever show data columns, never functions.

# The optional onEdit hook

if (typeof onEdit === 'function') onEdit(key, currentRaag[key]);

Since onEdit might genuinely be undefined (nobody's obligated to pass a third argument), calling it blindly — onEdit(key, currentRaag[key]) with no check — would throw an error the moment somebody calls renderRaagTable(currentRaag, containerEl) with only two arguments. The typeof onEdit === 'function' guard makes the callback truly optional: call it only if the caller actually supplied a real function.

This is the hook you're meant to use for recomputation — see the example wiring at the bottom of the source file, and the callback in fromHumanReadable/change handler flow covered fully next.

# The render cycle, start to finish

Every concept above comes together in one loop:

  1. Something calls renderRaagTable(currentRaag, containerEl, onEdit) the first time — e.g. right after your ChucK-mirroring calculator finishes computing currentRaag.
  2. The function clears containerEl, builds a fresh <table>, and loops over Object.keys(currentRaag), building one row per property using everything in createElement & friends.
  3. If the person edits an editable box and moves away from it, the browser fires a 'change' event, which calls the small arrow function registered back in Events.
  4. That callback parses the typed text back into real data (fromHumanReadable), writes it onto currentRaag[key], calls your onEdit hook if you gave it one (this is where you'd recompute everything derived from aaroh/avaroh), then calls renderRaagTable again — recursively — to redraw the whole table with fresh values.
  5. Because step 2 always starts by clearing the container, there's no leftover DOM from the previous render to clean up or worry about — the new table simply replaces the old one completely.
🎼 ChucK bridge

This "state changes → throw away the old output → rebuild it fresh from current state" shape is a genuinely common pattern in JS UI code (frameworks like React formalize it as their core idea), so it's worth recognizing by name now: rather than trying to patch the existing table in place (find the one changed cell, update just that), it's often simpler and less error-prone to just regenerate the whole thing from scratch whenever anything changes. At small scale — 80 rows — the cost of rebuilding everything is invisible to a person clicking around, so simplicity wins over micro-optimizing.
